# Sekoci Vue Frontend — Shared Conventions

One Vue 3 + TypeScript + Vite app at `web/`, talking to the 6 Go
microservices directly (no gateway — each service already sets CORS for
`http://localhost:5173`). The shell (routing, auth, layout, brand styling,
API client factory) is already built — domain agents add views/services/
routes into their own files only. Read this whole doc before writing code;
it tells you exactly which files are yours and which are shared/read-only.

## Stack already wired up

Vue 3 (`<script setup>` + Composition API), TypeScript, Vite, Vue Router 4,
Pinia, Axios. Don't add a UI component library (Vuetify/Element etc.) —
plain CSS using the classes in `src/style.css` (`.btn`, `.btn-primary`,
`.btn-accent`, `.btn-outline`, `.btn-danger`, `.card`, `.badge`,
`table.data-table`) plus scoped `<style>` per component, matching the
existing `LoginView.vue`/`AppLayout.vue` for visual style.

## Brand

Navy `#001f60` (primary), Teal `#3dd6c8` (accent), White `#ffffff`. CSS
variables already defined in `src/style.css` (`--sekoci-navy`,
`--sekoci-teal`, etc. — use these, don't hardcode hex). The client's spec
also calls for "design elements dengan opasiti rendah" (low-opacity design
elements) — see `--sekoci-navy-soft` / `--sekoci-teal-soft`, already used
for the active nav-item and role badge; reuse that same low-opacity
treatment for things like status badges, empty states, and section
dividers rather than inventing new colors.

## Directory ownership — READ THIS FIRST

You are one of 6 parallel agents, each owning ONE domain, each mapping 1:1
to a Go backend service that's already built, running, and documented
(read that service's own README.md for its exact API — that's your source
of truth for request/response shapes, not this doc). Every domain agent
touches ONLY:

- `src/views/<domain>/*.vue` — your views, organize into subfolders per
  role if that helps (e.g. `src/views/exam/admin/`, `src/views/exam/guru/`,
  `src/views/exam/siswa/`) — your call.
- `src/services/<domain>.service.ts` (one file, or split into
  `src/services/<domain>/*.ts` if you prefer — your call) — thin wrapper
  functions around `api('<domain>')` from `src/api/client.ts` (already
  built, handles JWT attachment + 401 redirect — just call
  `api('identity').get(...)` etc., don't build your own axios instance).
- `src/router/domains/<domain>.routes.ts` — THE ONLY router file you touch.
  It's a plain `RouteRecordRaw[]` already exported and already wired into
  `src/router/index.ts` (which you do NOT need to touch — it imports your
  array by name already). Routes nest under a layout wrapper, so use
  RELATIVE paths with no leading slash (e.g. `path: 'sekolah'` not
  `path: '/sekolah'`).
- Component-local files under `src/components/<domain>/` if you want
  shared sub-components within your own domain (don't reach into another
  domain's folder).

Do NOT touch: `src/router/index.ts`, `src/layouts/AppLayout.vue`,
`src/stores/auth.ts`, `src/api/client.ts`, `src/style.css`, `src/App.vue`,
`src/main.ts`, or any other domain's folder. If you think one of those
needs a change, note it in your own summary instead of editing it — six of
you are running at once and those files are the one shared surface, so
editing them is a guaranteed conflict.

## Routing & sidebar (how your routes.ts should look)

The sidebar in `AppLayout.vue` is auto-generated by scanning
`router.getRoutes()` for `meta.navGroup` + `meta.navLabel`, filtered by the
caller's `active_role` against `meta.role`. You don't touch the sidebar
code — you just set `meta` correctly on every route you want visible in
nav (omit `navGroup`/`navLabel` for routes that shouldn't appear in nav,
e.g. a detail/edit page reached by clicking a list row).

```ts
// src/router/domains/academic.routes.ts
import type { RouteRecordRaw } from 'vue-router'

export const academicRoutes: RouteRecordRaw[] = [
  {
    path: 'akademik/kelas',
    name: 'academic-classrooms',
    component: () => import('../../views/academic/ClassroomListView.vue'),
    meta: {
      role: ['admin', 'superadmin'],
      navGroup: 'Akademik',
      navLabel: 'Data Kelas',
    },
  },
  {
    // Not in nav (no navGroup/navLabel) — reached by clicking a row above.
    path: 'akademik/kelas/:id',
    name: 'academic-classroom-detail',
    component: () => import('../../views/academic/ClassroomDetailView.vue'),
    meta: { role: ['admin', 'superadmin'] },
  },
]
```

**Dashboards specifically**: register your role's dashboard route with
`name: 'dashboard-<role>'` exactly (e.g. `dashboard-admin`,
`dashboard-guru`) — `DashboardRedirectView.vue` looks up that exact route
name after login and forwards to it. If your domain doesn't own a role's
main dashboard, skip this — not every domain needs to own one.

## Auth store (`src/stores/auth.ts`, read-only reference)

```ts
const auth = useAuthStore()
auth.isAuthenticated // boolean
auth.activeRole // 'superadmin' | 'admin' | 'guru' | 'siswa' | null
auth.jabatan // string[] — Walikelas/Kepala Sekolah/Kepala Yayasan tags, no dashboard of their own
auth.schoolId // string
auth.userId // string
auth.switchRole('admin') // reissues JWT with a different active_role, no re-login
```

Router guards already enforce `meta.role` against `activeRole` — your view
components can assume they're only rendered for an allowed role, but if a
feature ALSO varies behavior within one role by `jabatan` (e.g. "Kepala
Sekolah dapat menilai semua guru" inside evaluation), check
`auth.jabatan.includes('Kepala Sekolah')` yourself in that component.

## API client (`src/api/client.ts`, read-only reference)

```ts
import { api } from '../api/client'
const res = await api('exam').get('/exams', { params: { classroom_id } })
res.data.data // the Envelope's `data` field — see src/types/envelope.ts
```

`api(service)` takes one of `'identity' | 'academic' | 'attendance' |
'exam' | 'evaluation' | 'report'` and returns a configured Axios instance
(JWT attached automatically, base URL from `VITE_<SERVICE>_URL` env var,
401 → auto logout + redirect to `/login`). Every response is the
`Envelope<T>` shape from `docs/CONVENTIONS.md` (`{ data, meta?, message,
errors }`) — unwrap `.data.data` for the payload, check `.data.errors` for
field-level validation errors to show under form inputs.

## Verifying your work

1. `cd web && npx vue-tsc -b` — this type-checks the WHOLE app, and five
   other agents are editing other files in this same project concurrently
   right now, so a failure pointing at a file outside your own domain
   folders is likely a sibling agent's in-progress work, not yours — don't
   try to fix or wait on it. Only fix errors in files under your own
   `src/views/<domain>/`, `src/services/<domain>*`, and
   `src/router/domains/<domain>.routes.ts`. A final unified check across
   all 6 domains happens after everyone lands (not your job).
2. `npm run build` — same caveat as above; a failure isolated to another
   domain's file isn't yours to fix.
3. The full backend stack is already running via `docker compose up -d`
   at the repo root (`/Users/tia-nurul/Documents/LMS/skci/`) — all 6
   `/healthz` respond on 8081-8086. Don't tear it down.
4. Run the dev server on YOUR OWN port to avoid colliding with the other 5
   agents testing at the same time: `npm run dev -- --port <your-port>`
   using identity=5173, academic=5174, attendance=5175, exam=5176,
   evaluation=5177, report=5178. Log in via `LoginView.vue` (seeded
   superadmin: `superadmin@sekoci.local` / `Sekoci@2026` — for
   admin/guru/siswa-scoped testing, create a school + user through the
   superadmin flow first, or check that service's README for its own
   seed/test data) and click through your actual pages — curl-testing the
   API alone doesn't prove the UI works. You don't have a screenshot
   tool; describe in your summary what you clicked through and what you
   saw (or say plainly if you could only verify by build + manual
   reasoning about the DOM, not an actual rendered check).
5. Stop your dev server when done so the port is free for anyone re-running it.
